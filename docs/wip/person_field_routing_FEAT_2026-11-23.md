## 1. 問題與動機

用一段描述實測 AI 整理（2026-11-23 第三次）：備註已經一件事一項，但 12 項建議裡有 5 項落在備註：

| 落在備註的 | 其實是 |
|---|---|
| 下班走到大江戶線搭車 | 生活圈、通勤 |
| 持人文簽證，效期 5 年 | 身分、證件 |
| 沒當過兵 | 身分 |
| 好像有駕照，但不常開（胥樊說的） | 證照 |
| 做包包的那家公司也在六本木 | 工作的細節（不確定是哪份工作） |

另外兩份打工被記成「ユニクロ（～？）：打工」「公司不明（～？）：在拉麵炒飯店打工」。

這不是提示詞再補一條規則能解決的：**現有欄位裡沒有放這些事的地方**，模型只能丟進備註——`person_career_goals` §14.1 說過的「什麼都丟進來會變雜物區」。

同時，提示詞已經有「一直打補丁」的跡象，再照這個方式加欄位會更亂：

1. **範例都來自同一段測試文字**：第 1、3、6、7 條的例子（包包的公司、胥樊說的、駕照、拉麵炒飯、second street、丸之內線通勤）幾乎都出自使用者那一段描述。規則被「訓練」在一個案例上，下次用同一段話測也就看不出規則本身好不好。
2. **「什麼放哪裡」散在各處**：目標（第 4 條）、家人（第 5 條）、欄位清單（第 6 條，只有中文名稱）、興趣／經歷／目標的分工（第 6 條裡一段）、備註是最後的地方（第 6 條末尾），每加一個欄位就要在好幾處補文字，沒有任何檢查會發現漏了。
3. **欄位的時間意義寫死在兩個地方**：提示詞第 6 條逐一列出「經歷是那件事的時間、興趣是開始的時間…」，LLM 輸出模型 `IngestListUpdate.time_start` 的說明又列一次；加欄位要記得兩邊都改。
4. **「不推測」和「重新組織語言」之間沒有界線**：第 1 條「絕不推測或補充」、第 7 條「重新組織成通順的說法」；模型把「江戶線」寫成「大江戶線」算哪一種，規則沒說。使用者的期望是：**有把握的校正要做**（錯了可以自己改回來）。

## 2. 目標與非目標

**目標**
- G1 簽證、在留資格、永住、駕照、已取得的證照、兵役有自己的欄位，記得下種類、取得與到期。
- G2 通勤、常去的地方、作息這類生活的事實有自己的欄位。
- G3 「什麼放哪裡」只有一個來源：每個欄位自己帶 LLM 用的分工說明，提示詞從欄位定義產生分工表；漏寫說明時測試失敗。加欄位不必再改提示詞的文字。
- G4 規則用原則與多樣的範例表達，範例不取自實測的文字。
- G5 名稱的錯字、簡稱、語音辨識錯誤，有把握時改成正確的名稱；沒把握時照原文。
- G6 打工記成工作經歷時不出現「公司不明」；知道是哪份工作的細節記進那份工作的說明。

**非目標**
- 讓 AI 建議目標「達成／放棄」或劃掉待追蹤（目前只能新增；另案，見 §6）。
- 把既有卡片備註裡的內容搬到新欄位（目前的人脈卡很少，需要時手動搬）。
- 簽證到期的自動提醒（欄位先記下到期日，提醒另案）。

## 3. 設計決策

### D1 新增兩個會變的欄位

沿用會變的欄位（`PERSON_HISTORY_FIELDS`）：一筆一筆記，系統記登錄日，不再適用時劃掉保留——簽證換了、駕照過期、搬家換了通勤路線，舊的仍是聊天素材。

| | `Credentials`（身分與證照） | `Daily_Life`（生活圈與日常） |
|---|---|---|
| 放什麼 | 簽證與在留資格、永住或歸化、國籍、駕照、**已取得**的證照與資格、兵役 | 通勤路線、常去的地方、住家或公司附近的生活圈、作息、固定的生活習慣 |
| 不放什麼 | 還在追求的（→ 目標）、語言程度與語言檢定（→ 語言）、學位（→ 學歷） | 喜歡的活動（→ 興趣）、住在哪（→ 現居地）、吃喝與愛去的店（→ 飲食喜好） |
| 一筆的鍵 | `value`（例如「人文簽證」「普通駕照」「沒當過兵」）、`since`（取得）、`until`（到期）、`note`（例如「效期 5 年」「不常開」） | `value`（一句話，例如「下班走到大江戶線搭車」） |
| 單值／短項目 | 都不是（可以同時有好幾筆） | 都不是 |
| 卡面 | 「認識脈絡與基本資料」一段，接在語言後面；到期日顯示在內容後面 | 同一段，接在現居地後面 |
| TG 清單代號 | `CR` | `DY` |

- 到期的鍵叫 `until`，**不能叫 `end`**：`is_active` 與卡面的 `isActiveEntry` 把有 `end` 的一筆當成已劃掉（學歷用 `finish` 也是這個原因）。
- 時間鍵是 `("since", "until")`，對應 LLM 輸出的 `time_start`、`time_end`，和工作經歷、學歷的對應方式相同（`HISTORY_PERIOD_KEYS` 的第一、第二個鍵），LLM 輸出格式不用改。
- AI 話題（`person_profile_topics.py`）會自動讀到兩個新欄位；身分與證照不算敏感（不加進 `EXCLUDED_FIELDS`），有需要的人可以放「敏感話題」。

### D2 「什麼放哪裡」改由欄位定義產生

- 每個會變的欄位與可更新的文字欄位，在 `backend/app/schemas/person_profile.py` 帶一段**給 LLM 的分工說明**（`FIELD_GUIDES`：放什麼、不放什麼，各附一兩個例子），以及有時間鍵的欄位每個鍵的意義（`FIELD_TIME_HINTS`，例如興趣的 `since` 是「從什麼時候開始」）。
- 提示詞的「放哪裡」改成一張表，依序是：這次見面的話題 → 互動；之後要問的、答應的 → 待追蹤；正在追求的 → 目標；家人與寵物 → 家人；接著逐一列出欄位（英文名稱、中文名稱、分工說明、時間的意義）；**都放不進的才放備註**（備註自己的說明就是這句）。
- 測試：每個會變的欄位與可更新的文字欄位都有分工說明、有時間鍵的欄位每個鍵都有說明，少一個就失敗。加欄位時忘了寫說明會在測試發現，不會等到實測。
- 提示詞第 6 條逐一列出的時間意義、`IngestListUpdate.time_start` 說明裡的欄位列舉，都改成「意義見各欄位的說明」。
- 欄位定義的表單說明（`_rows(title, description)`，例如「輸入後按 Enter 加入」）是給人看的，和給 LLM 的分工說明分開，不共用。

### D3 提示詞改寫成原則＋範例，不再逐案補規則

整理原則改成下面五條，各條是一個概念，不再有針對單一案例的條目：

1. **內容只來自文中**：不加文中沒有的事、不推論、不從一件事衍生出另一項建議；不確定的保留不確定的語氣；別人轉述的記下來源。`reason` 照抄原句。
2. **有把握的校正不算補充**（G5）：專有名詞（路線、地名、公司、學校、品牌、人名）的錯字、簡稱、語音辨識錯誤，有把握時改成正確的名稱；沒把握時照原文。`reason` 仍是原句，使用者對照得出改了什麼，改錯可以自己改回來。
3. **時間換成日期**：相對時間以今天換算（含寫進內容的時間，「大約 2026-09」）。
4. **放哪裡**：D2 的分工表；一件事一項（文字欄位的 `append` 也是）；能放進專門欄位的不放備註。
5. **整理成之後一看就懂的說法**：補上省略的主詞、把口語講清楚，只改說法不改意思。

各容器的格式規則（待追蹤的三種類型、目標的類型與時間、家人、工作經歷、清單的新增與劃掉、文字欄位的取代與接在後面）留在各自的段落，內容不變，只拿掉和第 1–5 條重複的部分。

**範例的原則**：規則與輸出範例的例子**不取自實測用的文字**，並涵蓋不同的人（工程師、學生、自營業者）；實測用的描述另外存成測試案例（§5）。現有範例裡出自同一段測試文字的（包包的公司、胥樊說的、駕照、拉麵炒飯、second street、丸之內線）全部換掉。

### D4 工作經歷：打工與工作細節

- 打工也是工作經歷：`job_title` 填「打工」，`value` 填店名；不知道店名時填店的種類（「拉麵店」），不留空、不出現「公司不明」。只想當聊天素材的打工經驗（「在澳洲打工度假」）放經歷。
- 工作的細節（公司在哪、做什麼產品）：知道是哪一份工作時，寫進那份工作的 `note`；不確定是哪一份時才放備註，照原文的不確定（「做包包的那家公司也在六本木」）。

### D5 上線順序（加欄位要完整同步一次）

同 `person_career_goals` §13.3、§14.3，**順序不能反**（新的後端寫入 Anki 還沒有的欄位會失敗）：

1. 所有裝置先同步。
2. 跑遷移（先不加 `--apply` 看計畫，確認只加 `Credentials`、`Daily_Life` 兩個欄位與換模板）：

```bash
python scripts/local_anki/Person_Profile_Dark/migrate_single_card.py
```

```bash
python scripts/local_anki/Person_Profile_Dark/migrate_single_card.py --apply
```

3. 在 NAS 的 Anki 做完整同步，選「上傳到 AnkiWeb」；其他裝置再下載。（使用者操作）
4. 部署後端與前端。

遷移後、部署前，舊的後端照常可用（它不碰新欄位）。

### D6 審查後的修正（2026-11-23，多面向審查：程式、測試、註解、型別）

- **續簽的新增被丟掉**（Important）：身分與證照是第一個「同一個內容、時間會換新」的欄位。LLM 照提示輸出「劃掉舊的簽證＋新增同名、新到期日的一筆」時，新增被當成已知而丟掉，寫入後只剩劃掉的那筆。→ `proposals_from` 先處理劃掉、再處理新增，同一批要劃掉的那筆不算已知；劃掉的建議排在前面，寫入時也先劃掉。劃掉又新增一模一樣（沒有新時間或說明）的，兩個建議互相矛盾，新增略過並記 log；只給新到期日、沒劃掉舊的，也略過並記 log。提示詞的到期說明加上「續簽、換了新的：劃掉舊的那筆，再新增一筆」。
- **說法互相矛盾**：工作經歷 `value` 不知道時填什麼（提示詞、LLM 輸出模型、打工的說明三處不同）→ 統一成「公司或店名；不知道名字但知道種類時填種類；連種類都沒提才空字串」。整理原則第 4 條原本「依順序放進第一個合適的地方」把互動排第一，剛拿到的簽證這類近況可能只進互動 → 改成列出各自放什麼，互動只放話題與一時的近況。生活圈的例子和興趣重疊 → 寫明活動本身是興趣、固定的時間地點路線才是生活圈。
- **型別與不變條件**：上面列的 import 時檢查；建卡表單的身分與證照改成單行（和項目模型一致）；`labels` 的型別改成可能沒有（`Partial`）。
- **網頁對話框的可切欄位**：列出所有能改的鍵後，興趣等可切欄位在網頁也能填時間；一次寫了好幾項又填時間時擋下並說明（TG 與整理本來就不這樣做）。
- **過時的註解**：多處還寫著「有說明／有起訖的只有職位、學歷」、`HISTORY_PERIOD_KEYS` 的 LLM 鍵名寫錯（應為 `time_start`／`time_end`）並補上「第二個鍵不能叫 `end`」的規則、遷移腳本的說明補上這次的兩個欄位。
