# 三語對話卡：網頁建卡（LLM 生成說法）

日期：2026-10-30　分支：`feat/person-profile`　卡片：`Speaking_Trilingual_Dark`　handler：`speaking_trilingual`

## 1. 目的

遇到「這句話不知道怎麼說」的場景時，能在網頁上很快建好一張三語對話卡：寫下背景，LLM 生成中、日、英三語
母語者真的會說的說法，每句附熟識度與簡短說明，勾選後建卡。

生成準則：**先自然，再打分**。每一句必須是母語者在這個場景裡真的會說的話，寫出來之後才判斷它的熟識度；
不是先定好熟識度，再為了湊那個分數去造句。

入口只開網頁；TG 不動。

## 2. 決定

| 項目 | 決定 |
|---|---|
| 一張卡的範圍 | 一個場景一張卡；同一場景不同熟識度、不同立場（答應／拒絕…）的說法都放在同一張 |
| 每句的資料 | 句子、說明、熟識度三項；說明存在參考答案那筆 JSON 的 `note` 鍵，不改筆記類型的欄位 |
| 說明的內容 | 中文、一兩句：用在什麼對象與場合、語氣上的重點，也可以是對場景的補充 |
| LLM 呼叫 | 單次請求，結構化輸出；每句的輸出順序是「句子 → 說明 → 熟識度」 |
| 句子數量 | 寧多勿少，讓使用者挑；但每句都要自然且有學習價值，不濫竽充數（見 §4） |
| 重新生成 | 不提供。生成不理想代表提示詞要改進 |
| 預覽 | 每句預設勾選，可取消；卡面的情境（`Prompt`）與補充（`Context`）可以直接修改 |
| 結束 | 「建立」寫入 Anki；「廢棄」直接丟掉草稿，不寫任何東西 |
| 草稿 | 不存在後端；生成結果只回給網頁，建卡時把勾選的句子送回來 |

## 3. 使用流程（網頁）

建卡頁選「三語對話卡」後：

1. **背景**（必填，多行）：發生什麼事、自己的處境。例：「朋友約我這週末去爬山，但我已經跟家人有約了。」
2. **想怎麼答**（選填，多行）：例：「婉拒，改約下週」。
   - 有填：生成表達這個意思的各種自然說法。
   - 沒填：由 LLM 想出這個場景下所有正反可能的自然回應（答應、拒絕、保留……），每種回應再給不同對象的說法。
3. **對象**（下拉選單）＋**對象補充**（選填，單行自由輸入）：
   - 下拉選項：不指定（各種對象）、長官或重要客戶、初次見面或店員與客人、同事、朋友、家人或伴侶。
   - 對象補充例：「房東，年紀比我大」。下拉選「不指定」但有填補充時，以補充為準。
   - 指定了對象時，只生成對這個對象自然的說法；熟識度照樣依句子本身評，不強迫落在某個分數。
4. 按「生成」：等待 LLM（顯示進行中；失敗時顯示原因與模型設定名稱，可以再按一次）。
5. **預覽**：
   - 上方是卡面的情境與補充，可直接修改。
   - 下方中、日、英三區，每句一列：勾選框（預設勾選）、熟識度刻度條（與卡片背面同款配色）、句子、
     小字說明。依熟識度排序，與卡片背面一致。
   - 區塊標題顯示「已選 N／M」。
6. 「建立」（至少勾一句才能按）或「廢棄」。建立成功後顯示筆記 ID 與連到卡片的連結，表單清空回到步驟 1。

牌組沿用建卡頁既有的牌組選擇（`deck="selected"`）。

## 4. 生成準則（提示詞 `Speaking_Trilingual_Generate.j2`）

提示詞的重點，依重要程度：

1. **自然優先**：每句都要是母語者在這個場景裡真的會說出口的話（口語、會話語氣），不是教科書翻譯。
   三種語言各自從場景出發去想，不是把中文翻成日文、英文。每句只用那個語言（實測出現過「family の予定」）；
   不編人名、公司名、數字等場景沒提到的細節（實測出現過「陳經理」），稱呼用通用的稱呼。
2. **先寫句子，再判斷**：輸出結構固定為 `content → note → familiarity`。熟識度是對已經寫好的這句話
   下判斷：「這句話會對什麼關係的人說」。禁止先定熟識度再造句。
3. **數量**：使用者會從中挑選，所以盡量列出母語者實際會用的各種說法；沒指定想怎麼答時，涵蓋正反各種回應。
   但「多」不等於濫竽充數：每一句都要自然、而且有學習價值（換了對象、立場或說法重點，學得到新的用詞或語氣）。
   兩句如果語氣、用詞幾乎一樣，只留一句；生硬、少見、只是改幾個字的句子不要列。三種語言的數量不必相同，
   熟識度的分布也不必相同（例如英文的語氣層次比日文少，少幾句是正常的）。
4. **熟識度刻度**：沿用評分提示詞的說明，讓生成與評分的標準一致：0＝正式場合、對重要客戶或長官（最客氣），
   3＝初次見面、店員與客人，5＝同事，7＝朋友，9＝家人（最親密、最隨意）。
5. **說明**：一律繁體中文（實測日文句的說明曾整段寫成日文）、簡短；寫這句用在什麼對象與場合、語氣的關鍵（例如「ございます是鄭重語，對客人用」），
   或是對場景的補充（例如「這是答應但保留時間的說法」）。不重複句子的翻譯。
6. **卡面情境**：根據背景與想怎麼答，寫成卡片正面的中文情境（`prompt`，對學習者說「你……」），
   不寫對象（對象差異由各句的熟識度與說明呈現）；其他值得記下的背景放 `context`（可空），只整理場景寫到的事，
   不推測使用者的心情或動機。

### 4.1 LLM 輸出結構（`app/schemas/llm/speaking_trilingual.py`）

```json
{
  "prompt": "朋友約你這週末去爬山，但你已經跟家人有約了。請回應他。",
  "context": "",
  "zh": [{ "content": "…", "note": "…", "familiarity": 7 }],
  "ja": [{ "content": "…", "note": "…", "familiarity": 2 }],
  "en": [{ "content": "…", "note": "…", "familiarity": 8 }]
}
```

`familiarity` 以 schema 限定為 0–9 的整數；欄位順序即生成順序。

## 5. 資料

參考答案一筆的格式（建卡時由後端補上 `date`、`status`、`audios`）：

```json
{ "date": "2026-10-30", "content": "…", "note": "…", "familiarity": 7, "status": 1, "audios": [] }
```

- `note` 可省略；舊卡沒有這個鍵，照常顯示。
- 本機匯入腳本（`import_cards.py`）本來就原樣帶過未知的鍵，`note` 不需要額外處理；範例 JSON 加上 `note`。

## 6. 改動

### 6.1 後端

- **能力宣告**（`capabilities.py`）：放寬「網頁只能用 form 流程」的規則，網頁也可以用 `preview`。
  三語卡改為 `CreateCapability(supported=True, channels=("web",), flow="preview", deck="selected", note_type="Speaking_Trilingual_Dark")`。
- **草稿端點**（通用）：`POST /handlers/{name}/draft`，只生成、不寫入。
  - `BaseHandler` 新增 `DRAFT_PARAMS`（草稿輸入的 pydantic 模型）與 `execute_draft(params)`；只有 `flow="preview"`
    且開放網頁的 handler 才能用，其餘回 400（與其他不支援的操作相同）。
  - handler 清單多回 `draft_schema`，網頁的輸入表單照樣由 schema 產生（對象用 `x-ui: select`）。
  - LLM 失敗時沿用既有錯誤格式，訊息帶模型設定名稱。
- **生成服務** `app/services/speaking_trilingual_generate.py`：寫法比照 `person_profile_ingest.py`。
  - 路由 `route("speaking_trilingual", "三語對話卡：生成說法", capabilities={"llm"})`，可在模型設定頁換模型。
  - 用 j2 樣板組提示詞，結構化輸出驗證後回傳草稿。
- **建卡參數**（`SpeakingTrilingualCreateParams`）：`prompt`、`context` 之外多 `references_zh`／`references_ja`／
  `references_en`（每項 `content` 必填、`note` 選填、`familiarity` 0–9 或省略）。`execute_create` 補上
  `date`（今天）、`status: 1`、`audios: []` 後寫入三個參考答案欄位；熟識度沿用 `trilingual_familiarity.py` 的規則。
  沒帶參考答案時行為與現在相同（空陣列）。

- **反向代理**：`frontend/nginx.conf.template` 的 `/api/` 加 `proxy_read_timeout 180s`。實測生成一張要 40–60 秒
  （claude-code opus），nginx 預設的 60 秒會切斷草稿請求。

### 6.2 卡片背面（模板與 CSS）

- `Speaking_Trilingual_Dark_back.html` 的 `buildReferenceItem`：句子下方加 `<div class="ref-note">`（`textContent`
  寫入，不拼 HTML）；沒有 `note` 時不產生。
- `Speaking_Trilingual_Dark_style.css`：`.ref-note` 字體比句子小（約 0.8em）、顏色較淡、與句子之間留一點間距；
  手機版同樣縮小。
- 改完以 `update_templates.py` 推到正式 Anki。

### 6.3 前端

- `lib/handlerCapabilities.ts`：不用改（含 web 的管道本來就可選）。
- `lib/createForm.ts`：支援 `enum`（只能選的下拉，用於「對象」）。
- `CardGenerator.tsx`：`flow="preview"` 時改用 `components/generate/PreviewCreate.tsx`（「草稿輸入 → 預覽 → 建立／廢棄」）；
  牌組說明、schema 欄位、建立成功提示抽到 `components/generate/formParts.tsx`，兩種流程共用。
- 新元件 `TrilingualDraftPreview.tsx`：情境／補充可編輯、三語分區（各有全選／全不選）、勾選、刻度條（配色與卡片相同；
  數字用一般文字色，淺藍在亮色主題上太淡）、說明小字。勾選與排序的邏輯在 `lib/trilingualDraft.ts`。
- 廢棄回到輸入畫面並保留輸入內容；生成中切換卡片類型會丟掉草稿（元件重新掛載）。
- `api.ts`／`client.ts`：`createDraft(handler, params)`；型別補 `draft_schema` 與三語建立參數。

## 7. 測試

- 後端：
  - 能力宣告的新規則（web＋preview 合法；未開放 preview 的 handler 呼叫草稿端點回 400）。
  - 生成服務：LLM 回傳轉成草稿；熟識度超出範圍、欄位缺漏時的錯誤；提示詞以各種輸入（有／無想怎麼答、
    不指定／指定對象、有補充）都能渲染（StrictUndefined）。
  - 建卡：參考答案寫入格式（`date`、`status`、`audios`、`note`、`familiarity`）；不合格的熟識度被擋下；
    沒帶參考答案時與現在相同。
- 前端：`handlerCapabilities` 的 preview 判斷；預覽的勾選與「至少一句才能建立」。
- 實際以真實 LLM 跑幾個場景檢查品質（自然度、數量、說明、熟識度合理），結果不好就改提示詞。
- 卡片：以靜態預覽確認說明的字體、顏色與手機版排版。
