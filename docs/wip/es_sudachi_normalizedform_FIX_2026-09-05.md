## 1. 問題

### 1.1 觸發點

2026-09-05 核心動詞 dry-run(`--skip-narrator`)中,344 個動詞有 **123 個 0 張**。逐一歸因後是五種不同的事:

| 原因 | 動詞數 | 性質 |
|---|---|---|
| 配額已滿(已生成 ≥20) | 21 | 正常 |
| 已生成但候選用盡 | 33 | 正常 |
| `--skip-narrator` 把候選全數濾掉 | 37 | 使用者的取捨,本計畫不處理(§6.1) |
| **ES 檢索零命中** | **26** | **本計畫處理** |
| 驗證器全數拒絕 | 6 | 多數合理 |

### 1.2 根因:`sudachi_baseform` 只還原活用形,不統一表記

索引 `fluencytides_dialogue` 的 analyzer 是 `sudachi_tokenizer` + `sudachi_baseform` + `sudachi_part_of_speech`,插件 `analysis-sudachi` 已裝。設定本身沒錯,問題在 `baseform` 這個 filter 的職責範圍:它把活用形還原成辭書形,**但同一個詞的不同寫法仍是不同 token**。以 `_analyze` API 實測:

| 原文 | `baseform`(現行) | `normalizedform` |
|---|---|---|
| 気付いた | `気付く` | `気付く` |
| 気づいた | `気づく` ← 對不上 | `気付く` ✅ |
| もらった | `もらう` ← 對不上 | `貰う` ✅ |
| バレる | `バレる` ← 對不上 | `ばれる` ✅ |
| という | `いう` ← 對不上 | `言う` ✅ |
| いった | `いく` ← 對不上 | `行く` ✅ |
| 逢った | `逢う` | `会う` ✅ |
| 捜した | `捜す` | `探す` ✅ |

母卡表記與語料表記只要一邊不同,查詢就落空:**気づく**(母卡)vs **気付く**(語料 244 句)→ ES 命中 0;**ばれる** vs **バレる** → 0;**貰う** vs **もらった** → 只撈到 6 句。

### 1.3 影響規模(句數口徑、只算獨立用法)

> 先前以 token 次數對句數得出「漏 9,865 句」是高估——把驗證器規則③本來就拒絕的補助動詞用法(〜ておく、〜てもらう)算了進去。以下為修正後的口徑。

17 個常用動詞,ES `MATCH` 句數 vs UniDic 判定為獨立用法的句數:

| 動詞 | ES | 應撈到 | 召回 |
|---|---|---|---|
| 見る / 話す / 作る | 1,066 / 246 / 288 | 1,055 / 237 / 286 | 101–104% |
| 思う / 置く / 来る / 呼ぶ | 2,259 / 99 / 617 / 114 | 2,341 / 104 / 659 / 121 | 94–96% |
| 聞く | 489 | 597 | 82% |
| 会う | 88 | 152 | 58% |
| 行く | 772 | 1,471 | 52% |
| 言う | 2,722 | 5,830 | 47% |
| **貰う** | **6** | **103** | **6%** |
| 合計 | 9,592 | 13,959 | **69%** |

**ES + Sudachi 的組合本身沒有問題**——多數動詞召回 94–104%;缺口集中在表記有變體的詞。這是設定問題,不是選型問題。曾一度考慮改用 MySQL 的 lemma 索引(`build_nlp_index.py` 的 `dialogue_verbs_index`,該表在 DB 中並不存在)取代 ES,實測 analyzer 後確認不必:ES 內建的 `sudachi_normalizedform` 做的正是同一件事,不需另建表、不需改檢索程式。

## 2. 方案

### 2.1 ES:換一個 token filter

`elasticsearch_client.py::recreate_index()` L108:

```diff
 "filter": [
-    "sudachi_baseform",
+    "sudachi_normalizedform",
     "sudachi_part_of_speech"
 ]
```

表記對應表內建在 Sudachi 辭書的「正規化表記」欄,不需要應用層邏輯或對照設定。

**為什麼查詢端不用改**:`dialogue` 的 mapping 只宣告 `analyzer`、沒有 `search_analyzer`,ES 預設查詢時沿用同一個 analyzer,索引端與查詢端必然一致:

```
現在:  查詢「気づく」→ 気づく  ✗  索引裡的「気付いた」→ 気付く
改後:  查詢「気づく」→ 気付く  ✓  索引裡的「気付いた」→ 気付く
```

`search_dialogue_by_verb()` 送出的字串不變,比對在 ES 內部完成。兩條生卡管線、讀音判讀腳本、標記工具共用這一個函式,一次修正全部受惠。自他動詞目前沒暴露此問題只是母卡清單裡剛好沒有這幾個詞,機制完全相同。

> **實作後修正(§4.4)**:analyzer 換掉後,`気づく`/`ばれる` 這類「母卡漢字 vs 語料漢字」的表記差確實不需要 `include_keywords` 了;但「母卡漢字 vs 語料**假名**」(貰う/もらった、履く/穿く、飲み込む/呑み込む)仍被 `search_dialogue_by_verb()` 的漢字 LIKE 擋住——LIKE 由**關鍵字自身**的漢字推導,母卡表記的漢字在假名句裡不存在。這一層不該拆(§2.2),所以 `include_keywords` 仍是必要的逃生門,只是要用實測資料逐個決定,見 §3 的設定檔列。

### 2.2 漢字 LIKE 防線保留,`include_keywords` 是逃生門

`search_dialogue_by_verb()` 對關鍵字的每個漢字片段加 `dialogue LIKE "*漢字*"`,用來擋 ES|QL `MATCH` 多 token 走 **OR** 的假陽性(實測 `食べ切る` 純 MATCH 回 470 句 = 食べる ∪ 切る;`どいて` 純 MATCH 回 17,157 句,因為切成 退く＋て 而 て 幾乎每句都有)。`normalizedform` 讓擬聲詞「ドクッ」也正規化成 `どく`,假陽性比以前**更多**,所以這道防線現在更不能拆。

代價是假名書きの變體被擋住。逃生門是 per-verb `include_keywords`:純假名關鍵字沒有漢字片段、不產生 LIKE 條件。但豁免的關鍵字必須是 Sudachi 下的**單一 token**——多 token 的假名關鍵字(`どいて`、`食べきる`)會直接觸發 OR 爆炸,LIKE 擋不住(它只檢查漢字存在,不檢查是不是那個詞)。

### 2.3 驗證器:表記兄弟防護(必要配套,不是可選項)

驗證計畫書時發現(2026-09-05):`normalizedform` 合併的異體字,**UniDic 在 lemma 層也合併同一批**(上げる/揚げる → lemma 上げる;下りる/降りる → 下りる;付ける/点ける → 付ける;溜める/貯める → 溜める;汚す/穢す → 汚す……)。而驗證器 `lemma_matches_target()` 是「lemma **或** orthBase 任一相符即通過」,於是出現**不對稱的誤收**(實測):

| 目標母卡 | 句子 | token lemma / orthBase | 驗證器 |
|---|---|---|---|
| 上げる | 天ぷらを**揚げた** | 上げる / 揚げる | 🚨 接受(lemma 相符) |
| 下りる | バスを**降りた** | 下りる / 降りる | 🚨 接受 |
| 付ける | 電気を**点けた** | 付ける / 点ける | 🚨 接受 |
| 溜める | お金を**貯めた** | 溜める / 貯める | 🚨 接受 |
| 揚げる | 手を**上げた** | 上げる / 上げる | ✅ 拒絕(兩者皆不符) |
| 降りる | 山を**下りた** | 下りる / 下りる | ✅ 拒絕 |

規範寫法的母卡會吃掉變體寫法的句子。**今天沒出事,只因為 ES 的 `baseform` 把兩種寫法切成不同 token,規範母卡根本撈不到變體句**——這是一道無意間的保護,換 `normalizedform` 後就消失。這些不是同一個詞的異體字,是**語意不同的動詞**(揚げる=炸、上げる=舉;降りる=下車、下りる=下來;点ける=開燈、付ける=附著;貯める=存錢、溜める=積累),誤收就是錯卡;去重鍵 `(script_id, verb_lemma, project)` 含 `verb_lemma`,同一句可在兩張母卡下各生一張。

**規模**:自他動詞 490 個表層在 `normalizedform` 下碰撞 **26 組**;語料中變體寫法真的出現 **8 組**;規範母卡會誤收 **6 組、約 52 句**:

| 規範母卡 | 變體 | 語料句數 |
|---|---|---|
| 上げる | 揚げる / 挙げる | 18 / 4 |
| 下りる | 降りる | 17 |
| 溜める | 貯める | 8 |
| 付ける | 点ける | 3 |
| 上がる | 揚がる | 1 |
| 溜まる | 貯まる | 1 |

核心動詞 344 個表層 **0 組碰撞**。其餘 18 組(汚す/穢す、痛む/傷む、覚める/醒める、返す/還す、助ける/扶ける……)變體寫法在語料中為 0 句,風險目前是理論的;母卡與語料都會變,所以防護必須是通用規則。

**規則**:token 以 lemma 命中目標時,若其 **orthBase ≠ 目標**,且該 orthBase **本身是同專案另一張母卡的表層**(「表記兄弟」),則拒絕。以 `sibling_surfaces: frozenset[str]`(該專案全部母卡表層)注入,與 `compound_seqs` 同一注入模式,**不寫任何動詞清單**,新增母卡自動納入。

- 目標 上げる、句 揚げた:lemma 命中,orthBase 揚げる ≠ 上げる **且 揚げる 是母卡** → 拒絕 ✅
- 目標 貰う、句 もらった:lemma 命中,orthBase もらう ≠ 貰う 但 **もらう 不是母卡** → 照常接受 ✅(假名書き召回不受影響)
- 目標 汚す、句 穢した:orthBase 穢す 是母卡 → 拒絕 ✅(けがす 的句子不該掛在 よごす 母卡下;連帶修掉一個潛在問題)
- 目標 揚げる、句 上げた:本來就拒絕,不變

新增拒絕原因常數 `REJECTION_ORTH_SIBLING = "屬其他表記母卡"`,漏斗報告會計數,驗收可直接看擋了幾句。

### 2.4 兩個變因分開量

先做 §2.3 的防護、在**改 ES 之前**跑一次 dry-run:因為今天 ES 撈不到變體句,防護應該零觸發、總數與基線完全相同(§4.2 #0)。確認後再改 ES filter 並重灌。這樣任何數字變化都能歸因到單一變因。

## 5. 風險與邊界

1. **重灌期間檢索不可用**。先刪後建,重灌 53,190 句需數分鐘,期間生卡/判讀腳本撈不到句子。**重灌前確認沒有其他腳本在跑。**
2. **正規化比原本激進,而驗證器擋不住**——已由 §2.3 處理。殘餘:若某組只有 Sudachi 合併、UniDic 不合併,驗證器本來就分得開,不需防護;反之只有 UniDic 合併、Sudachi 不合併的組,ES 撈不到,與今天相同。防護以「同專案全部母卡表層」為集合、啟動時重建,不需維護清單。
3. **所有 dry-run 基線作廢**。§4.1 的三個數字在改動後失效,以 after 為新基線。
4. **`--skip-narrator` 造成的 37 個 0 張動詞不在範圍**(§6.1)。
5. **與 fugashi/UniDic 詞典釘死(FEAT §8.4)互相獨立,但要知道兩者的表記合併剛好重疊**(同源於日文正規化慣例)。ES 放寬召回時驗證器不會自動變嚴,§2.3 正是補這個缺口。
6. **重灌前必須確認 ES 節點磁碟有空間**(2026-09-05 事故)。`recreate_index()` 是先 `indices.delete` 再建;當時磁碟 97% 滿,新索引的分片配不出來,舊索引已刪、新索引空的,檢索直接下線。`sync_mysql_to_es.py` 的「成功同步 N 筆」計的是**準備好的** action 數不是寫入成功數,而且 `except` 只印一行就走到「全量同步完成」——失敗時 log 看起來像成功。擴容後重灌才復原。資料本身無損(MySQL 是真實來源)。應在重灌前檢查 `_cat/allocation` 的 `disk.percent`,並讓 sync 腳本在 bulk 失敗時以非零退出。

## 6. 後續(本計畫不做)

1. **旁白過濾的粒度**:37 個動作描寫動詞(飛び出す、駆け寄る、通り過ぎる、微笑む、立ち去る……)的語料全在旁白,`--skip-narrator` 一開就全滅。可對這類動詞在 `verb_search_config.json` 個別放行,或不用全域旗標。
2. **VerbPair 的 Fetch-100 頭部偏差**:自他動詞每個關鍵字只抓 ES 前 100 筆且不分頁(`limit=100, last_script_id=0`),高頻動詞永遠只看到遊戲最前面的章節。CoreVerb 已改全量游標分頁,VerbPair 尚未跟進。改 ES 後候選變多,這個偏差會更明顯。
3. **兩條管線的 keyword 設定檔尚未統一**:`extra_search_keywords.json`(以 note id 為鍵)與 `verb_search_config.json`(以表記為鍵)是兩套獨立實作,只共用最底層的 `search_dialogue_by_verb()`。自他動詞這輪**沒有**做關鍵字分析,同樣的漏句(假名書き)在那邊也存在。
4. **關鍵字的單 token 啟動檢查**:`include_keywords` / `extra_keywords` 載入時以 `_analyze` 驗證每個關鍵字在 Sudachi 下是單一 token,多 token 記 WARNING 並忽略——與 `verb_lemma` 啟動防線同一模式。這輪是人工篩的,日後有人手滑加 `どいて` 就會炸。
5. **驗證器的三個既有弱點**(被漢字 LIKE 遮住,這輪透過假名關鍵字看見):
   - `〜がって＋補助動詞`:「面白がってもらえて」的 がっ 是 接尾辞 不是 動詞,規則③「動詞＋て＋動詞」不觸發,補助動詞用法被當獨立用法接受(漢字 貰える 同樣中招)。
   - `〜ないといけない / 〜ちゃいけない`:構式裡的 いけ lemma 是 行く,驗證器接受;`行く` 若日後加假名關鍵字就會混入。
   - UniDic 誤切:「そかそか」→ そ＋かそ[貸す]＋か。純假名關鍵字(如 かせる)會撈到,驗證器也接受。這是 LIKE 防線存在的根本理由,不該拆。
6. **同表層異讀的核心動詞**:`支える`(ささえる／つかえる)、`滑る`(すべる／ぬめる)在關鍵字分析中浮現——語料裡另一讀音的句子存在,CoreVerb 目前不傳 `expected_reading`,驗證器分不開。與 FEAT §7.3 的 UniDic 候選來源擴充是同一件事。
7. **`どく` 的 2 張損失**:等 `judge_verb_readings.py` 跑過 退く 三讀母卡後,整組重審是否要以手動 `extra_keywords` 或改母卡表記補回。
