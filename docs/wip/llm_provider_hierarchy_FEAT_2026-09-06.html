1. 問題與動機

1.1 現況：三個裸類別，契約靠文字

app/infrastructure/llm/client.py:57               class LLMClient:
app/infrastructure/llm/claude_code_client.py:84   class ClaudeCodeLLMClient:
app/infrastructure/llm/anthropic_client.py:134    class AnthropicLLMClient:

對照同一個 repo 語音軸線的 class GeminiNativeAudioEvaluator(BaseAudioEvaluator):，差別一眼可見。三者的契約目前靠工廠的 union 型別、三份 docstring、以及錯誤訊息裡的魔術字串 "LLM API 在所有重試後仍回傳空內容" 與 "Quota" 維繫——沒有一樣是型別系統。

代價已經在三處看得到：

  • app/core/dependencies.py:103 的型別註記寫 "LLMClient | ClaudeCodeLLMClient"，漏了 AnthropicLLMClient——union 已經對不上
  • runtime_config_service.py:131-133, 191-193, 234-246 只能用 getattr(llm_client, "_formatted_model_name")、hasattr(llm_client, "_build_env")，甚至直接呼叫 llm_client._build_env()——沒有可宣告的型別，服務層只能對私有屬性做反射
  • 2026-08-27 計畫 §D9 用一張表格逐項人工核對兩個 client 的行為一致性——那張表做的事，@abstractmethod 加一個抽象 property 就能讓 mypy 自動做

1.2 兩個新 provider 同時到來，而且落在不同的變化軸上

Antigravity CLI。agy -h 顯示它與 claude -p 同型：-p、--model、--effort、--output-format json、--json-schema 全部對得上。「subprocess CLI」現在有第二個成員，重疊的不是模型名，是整套機械流程——asyncio.to_thread(subprocess.run)、UTF-8 解碼、workdir / audit 解析、fence 清理 → json.loads → jsonschema.validate、帶回饋的修復重試、審計落盤。這些佔 ClaudeCodeLLMClient 六成以上行數。

Gemini 原生 SDK。目前文字軸線沒有原生 Gemini 實作，LLMClient 走 Google 的 OpenAI 相容端點。client.py:114-117 寫明該端點不認識 safety_settings，傳了直接 400；而 .env 的 LLM_BASE_URL 正是那個端點。

LLM_PROVIDER=google 這條路根本無法把安全閾值調到 BLOCK_NONE，但 galgame 台詞正是最容易觸發 PROHIBITED_CONTENT 的內容。原生 SDK 的 GenerateContentConfig 直接收 safety_settings 與 thinking_config，這是 OpenAI 相容層永遠給不了的。

1.3 已埋的坑（重構時順手拆）

  • factory.py:94-98 的 anthropic 分支 return AnthropicLLMClient()，既不傳 model 也不傳 effort。今天無害是因為 stub 一律拋錯；實作後兩個覆寫參數會靜默消失
  • factory.py:100 硬編碼「effort 覆寫僅 claude-code 支援」。第二個支援 effort 的 provider 一出現這行就錯——agy 有 --effort
  • 模型標籤推導有三份：client.py:110-112、claude_code_client.py（逐字重複）、scripts/common/llm_label.py；後者記著 2026-08-28 誤標 190 筆的前科
  • 錯誤分級靠字串：生成腳本三處 "…仍回傳空內容" in e.response.text。而 FluencyTidesError.error_code 本來就經 main.py:261 進 ErrorResponse——機制存在，只是 LLMServiceError 一律回 LLM_SERVICE_ERROR

2. 目標與非目標

目標

  • G1 BaseLLMClient(abc.ABC)，五個具體類全部掛上；mypy 可驗證契約
  • G2 能力旗標取代 provider 字串硬判；工廠不再認得任何 provider 名
  • G3 HeadlessCliLLMClient 承載 subprocess 共用流程；既有 40 項 claude 測試一行不改全綠
  • G4 GeminiNativeLLMClient：LLM_PROVIDER=gemini-native，safety_settings 四類 BLOCK_NONE
  • G5 AntigravityLLMClient：LLM_PROVIDER=antigravity
  • G6 三個 LLMServiceError 子類各帶 error_code；訊息文字保留識別字串
  • G7 標籤推導與 schema 工具各只剩一份
  • G8 既有 google / claude-code 兩條路逐位元一致（例外：拒答訊息依 D5 追加 PROHIBITED_CONTENT 說明；腳本側失敗紀錄的標籤改與後端一致）

非目標

  • 不做母公司層級的中間抽象（D1）
  • 原生 SDK 群不設中間層（D4）
  • 不改 LLMClient 的重試時序——helper 由新 client 首用
  • 不改生成腳本的分級表——error_code 遷移列 §8
  • 不實作 AnthropicLLMClient 本體——只掛基底、修正建構子收參數
  • 不動語音軸線

3. 設計決策

D1分組軸線：傳輸協定，不是母公司

繼承樹按「怎麼把 prompt 送出去、怎麼把 JSON 收回來」分，不按「模型是誰家的」分。兩個反例足以說明：ClaudeCodeLLMClient 與 AnthropicLLMClient 同屬 Anthropic，共用面積是零；Google、OpenAI、Yinli/DeepSeek 三個母公司卻共用同一個 LLMClient。

群成員中間層
OpenAI 相容 HTTPLLMClient（Google 相容端點、OpenAI、各中轉站）無——一個類別內以 provider 字串分流，分支只有兩處
原生 SDKGeminiNativeLLMClient（新）、AnthropicLLMClient（stub）無（D4）
subprocess CLIClaudeCodeLLMClient、AntigravityLLMClient（新）HeadlessCliLLMClient（D3）

D2BaseLLMClient：ABC 而非 Protocol，帶能力旗標與共用 helper

選 ABC 的三個理由，與 audio_evaluator/base.py 的論證一致：要強制子類實作、漏了在 import 時就炸；基底要放具體共用邏輯（統一的 model 解析、effort 支援檢查、_retry_transient），Protocol 放不了；工廠與 RuntimeConfigService 需要 isinstance 做能力分流，runtime_checkable 只檢查方法名存在。

D4原生 SDK 群不設中間層

兩個成員一個是 stub、一個尚未建；anthropic 是 messages.create + output_config.format + stop_reason，google-genai 是 generate_content + GenerateContentConfig + finish_reason，信封解析沒得共用。真正共用的只有瞬時錯誤重試，而 LLMClient 也需要它——所以放 BaseLLMClient._retry_transient()。若日後 refusal / safety 映射出現逐字重複再抽；由重複驅動，不由分類法驅動。

D5例外子類：error_code 取代魔術字串，訊息文字保留過渡

例外error_code拋出時機訊息必含（過渡期）腳本既有處置
LLMRetryExhaustedErrorLLM_RETRY_EXHAUSTED外層重試耗盡「LLM API 在所有重試後仍回傳空內容」記錄失敗、跳此句
LLMQuotaErrorLLM_QUOTA429 / 額度耗盡 / rate limit 信封「Quota」暫停 60 秒
LLMRefusalErrorLLM_REFUSALGemini finish_reason ∈ {SAFETY, PROHIBITED_CONTENT}；Anthropic stop_reason == "refusal"；claude-code 拒答「PROHIBITED_CONTENT」與「…仍回傳空內容」兩者皆含跳此句

error_code 零 API 改動即可到達腳本：FluencyTidesError.error_code 經 main.py:261 的 handler 進 ErrorResponse.error_code，腳本已收到該 JSON，只是沒讀那個欄位。腳本改讀 error_code 列 §8。

A9（P0 實測） generate_structured_data 收的是 dict schema，語音軸線是直接丟 Pydantic class。須確認目前安裝的 google-genai 收原始 dict 的方式（response_schema 直接吃 dict、或 response_json_schema），以及是否仍需 resolve_json_schema 展平——該函式當初就是為 Gemini 不吃 $ref 而寫。

實測結果（2026-10-14，google-genai 2.10.0、gemini-3.1-pro-preview、真實卡片 schema）：response_json_schema / response_schema × 原始 $defs / 展平，四種組合全數接受、輸出通過 Pydantic 驗證。定案用 response_json_schema + 展平（各 provider 送同一份 schema）。SDK 的 tenacity 重試預設關閉；裝了 aiohttp 時非同步請求走 aiohttp，其連線錯誤另有一次 SDK 內建重試（隨機 1–10 秒）。

#結論對實作的影響
A1-p 必須帶值、不讀 stdin（-p - 的 - 被當成字面 prompt）；stdin 只能走 --input-format stream-json，每行 {"event":"user","message":{…}}收發都用 stream-json，不帶 -p
A2stream-json 逐行輸出 init → step_update… → result；錯誤時也有 result 行。每次呼叫在 ~/.gemini 留一個會話檔取最後一個 event=result；殘留靠專用 home 隔離
A3--json-schema 由 CLI 強制，結果在獨立的 structured_output；response 混有散文與額外欄位讀 structured_output，不讀 response
A4預設開放約 60 個工具；workspace 內寫檔不需許可；執行命令被自動拒絕時 status 仍 SUCCESS、帶 denied_actions、無結果專用空 workdir；無結果時可重試並附「不要呼叫工具」回饋
A5會讀 ~/.gemini/GEMINI.md（模型逐字引出 FluencyTides 開發規範）；HOME / USERPROFILE 換到空目錄即隔離預設隔離 HOME（LLM_ANTIGRAVITY_ISOLATE_HOME）
A6憑證在 OS keyring，換 home 不影響認證；IDE 會設 ANTIGRAVITY_* 變數剔除 ANTIGRAVITY_*；容器認證未測
A7模型名錯 → invalid model selection；服務不可用 → Eligibility check failed: UNAVAILABLE (code 503)，當天約四成呼叫；用法錯誤 → exit 2、只有 stderr；未登入、額度未能觸發依 gRPC 狀態名分流；503 退避後重試
A8%LOCALAPPDATA%\agy\bin\agy.exe，現行安裝會加入使用者 PATH作為 PATH 未生效時的兜底候選
新--model 給基底名（gemini-3.8-flash），思考深度另給 --effort（五檔）；agy models 的 -low 等後綴是顯示名白名單放基底名
新會自動更新（實測期間自升 1.3.5、旗標行為改變）；AGY_CLI_DISABLE_AUTO_UPDATE 可關環境一律關閉自動更新
新整體耗時 8–163 秒，模型本身只佔 2–4 秒逾時維持 900 秒；吞吐量低於 claude-code

    "gemini-native": lambda: _import("gemini_native_client", "GeminiNativeLLMClient"),
    "anthropic":     lambda: _import("anthropic_client", "AnthropicLLMClient"),
}

def create_llm_client(*, model=None, effort=None) -> BaseLLMClient:
    provider = (settings.LLM_PROVIDER or "").strip().lower()
    client_cls = _LOADERS.get(provider, lambda: LLMClient)()
    return client_cls(model=model, effort=effort)     # 所有 provider 一律收兩個參數

惰性 import 慣例不變；effort 支援檢查搬進 BaseLLMClient.__init__，工廠不再有 factory.py:100 那行；未註冊的 provider 值一律回 LLMClient，與現況一致。

既有測試的攔截點必須保留。factory.py 頂層維持 from …client import LLMClient（test_claude_code_client.py:533,607 以 mock.patch("…factory.LLMClient") 攔截）；loader 以 importlib.import_module + getattr 在呼叫時解析類別，mock.patch.object(claude_code_client, "ClaudeCodeLLMClient")（:532,542,550）才仍有效。
