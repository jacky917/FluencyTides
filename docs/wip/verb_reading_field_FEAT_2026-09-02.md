## 1. 現況與需求

### 1.1 同表層多讀的實際規模(2026-09-02 全牌組掃描)

牌組 491 個不同表層中,**14 個表層、8 組動詞、18 張母卡**的漢字表記相同但讀音不同:

| 表層 | 讀音(母卡 note id) |
|---|---|
| 捲る / 捲れる | まくる(…540)/ めくる(…543) |
| 退く / 退ける | しりぞく(…654)/ どく(…657)/ のく(…661) **三讀** |
| 凝る / 凝らす | こる(…700)/ こごる(…702) |
| 止める | やめる(…711)/ とめる(…909032) |
| 開く / 開ける | あく(…748)/ ひらく(…750) |
| 温める | あたためる(…770)/ ぬるめる(…772)/ あたためる(…909007) |
| 解く / 解ける | とく(…830)/ ほどく(…832) |
| 汚す / 汚れる | けが(…921)/ よご(…802616341) |

### 1.2 兩個具體問題

**問題 A:去重鍵分不出母卡(資料層)**
唯一鍵 `(script_id, verb_lemma, project)` 對 `止める` 只認得一筆。目前 117 筆紀錄落在上述表層,尚無實際撞鍵(剛好挑到不同台詞),但**兩側正在互相擋**:任一張母卡用過的台詞,另一張就取不到。證據——`開く` 20 筆全來自 ひらく 側、`開ける` 20 筆全來自 あく 側、`汚す` けが 側只有 1 筆而 よご 側 6 筆。這不是未來風險,是現在進行式的配額餓死。

**問題 B:候選句歸屬需要上下文(內容層)**
ES 用表層搜,搜到的句子究竟讀哪個音,只有上下文知道。fugashi/UniDic 幫不上忙——它對同表層多讀是**上下文盲的固定選讀**(ドアが開く→ヒラク、お腹が空く→アク),這正是 `ignore_reading` 開關存在的原因。

已發現的實例:`[3332]`「うっ、うぅぅ……**汚された**、汚されちゃったよ……」(翻譯「我被玷汙了」)掛在 **よご** 母卡下,但該語境讀 **けがされた**,應屬 けが 母卡。

現有繞法只有 6/18 張母卡在 `extra_search_keywords.json` 設了假名關鍵字分流(まくる/めくる 等),且僅在語料剛好用假名書寫時有效——漢字寫法的句子仍會被兩側同時撈到。

### 1.3 為什麼讀音欄位不該由 LLM 生成

`verb_reading` 記的是「這筆紀錄屬於哪張母卡」,母卡標音是使用者**已聲明的事實**,不是待推斷的知識(全牌組 522 項標音已通過送假名一致性檢查,零可疑)。鍵欄位引入 LLM 的波動,等於重演剛修完的拼寫漂移問題。

分工因此明確:**母卡讀音 = 資料層身分(確定性取值);句子讀音 = 內容層判斷(需要上下文)**。前者解問題 A,後者解問題 B。

## 2. 設計:`verb_reading` 欄位

| 項目 | 決定 | 理由 |
|---|---|---|
| 型別 | `VARCHAR(32) NOT NULL DEFAULT ''` | 長度由實測推得:全牌組 522 項讀音最長 5 字(よこたわる 等)、平均 3.3,取 32 留 6 倍餘裕。`NOT NULL` 是硬性要求——唯一鍵內的 NULL 互不相等,會讓去重整個失效 |
| 值域 | 純平假名(`ぁ-ん` + `ー`) | 全牌組實測 522/522 導出即為純平假名 |
| 唯一鍵 | `(script_id, verb_lemma, verb_reading, project)` | 取代 `uk_script_verb_project` |
| 取值 | 母卡標音去 base:`纏[まと]める` → `まとめる` | 管線的 `_parse_verb_field` 已在算,只是沒用 |
| 共用 helper | `scripts/common/verb_lemma.py` 新增 `canonical_verb_reading()` | 與 `canonical_verb_lemma` 同檔,寫入點只准走這裡 |

**為什麼是 32 而不是 64**:`VARCHAR` 是變長儲存,32 與 64 在磁碟上佔用相同,但欄位會進唯一索引,而索引前綴長度按宣告上限計算(utf8mb4 每字元 4 bytes:32 → 128 bytes、64 → 256 bytes)。現有鍵已有 `verb_lemma VARCHAR(255)`(1020 bytes),離 InnoDB DYNAMIC 列格式的 3072 bytes 上限尚遠,兩者皆可行,但沒有理由讓索引多佔一倍。32 對最長 5 字的實測值仍有充足餘裕,足以吸收未來的長複合動詞,以及刪卡工具鏈既有缺陷(多值配對如「極まる, 窮まる」可能回傳整串)。

> `verb_lemma` 的 `VARCHAR(255)` 同樣遠超所需(最長表層 5-6 字),但那是既有欄位、改動要重建索引,屬另一件事,本計畫不夾帶。

**不採 `master_note_id` 作鍵**:母卡刪除重建會換 id(存量已見 `掛ける` 一張母卡消失、留下 3 筆孤兒紀錄),讀音跟著詞走更穩定。

**遷移零衝突**:新鍵比舊鍵寬鬆,加欄位時全部既有列 `verb_reading=''`,鍵等價於舊鍵,不可能撞。安全順序:**加欄位 → 回填 → 改鍵**。

**啟動防線**(沿用既有模式):生成前檢查該專案是否存在 `verb_reading=''` 的紀錄;有則中止並提示先跑回填,避免「空讀音 vs 有讀音」被視為兩筆而重生。

## 4. 問題 B 的實作:方案 A(提示詞拒絕)

管線是「母卡驅動」——拿母卡的動詞去 ES 撈語料,再逐句生成。讀音判斷放在**生成請求內**,因為那是整條管線唯一看得到完整上下文的地方。

### 4.1 機制

1. **啟動時建同表層讀音表**:腳本開頭已經要撈全部母卡,順手掃一次建 `{表層: {讀音}}`,只保留讀音數 > 1 的表層(§1.1 的 14 個)。不落設定檔——母卡改動即自動反映,無維護成本。
2. **payload 新增 `target_verb_reading`**:僅當該表層在多讀表中時才帶值(如 `けがす`),其餘 477 個表層不帶。
   - **`target_verb` 維持去標音表層不變**——它在模板裡有三處既有用途(標題、情境概要、自他判定),塞進標音會污染既有語意。讀音走獨立變數。
3. **模板新增條件區塊**(僅在有 `target_verb_reading` 時渲染):要求先判斷句中該動詞在此語境實際讀作什麼;若非指定讀音,回傳拒絕結構而非卡片內容。
4. **後端轉成 `READING_MISMATCH` 錯誤碼**(比照既有 `CLOZE_POSITIONING_FAILED`,422 + `error_code`),回應帶上模型判定的讀音供 log 追溯。
5. **腳本沿用既有分支**:`record_failure` 後跳下一句,不中止整批。

### 4.2 為什麼這樣切乾淨

- **拒絕即永久跳過,且不誤傷另一側**:`failure_count >= 1` 的既有規則會讓該句不再被同一組合重試——這正是想要的語意(這句本來就不屬於這張母卡)。而加了 `verb_reading` 後,兩張母卡的 failure 紀錄是不同的鍵,**けが 側的拒絕不會擋住 よご 側**。欄位與方案 A 互為前提,必須同一個單元交付。
- **只對 14 個表層啟用**:其餘 477 個表層沒有另一個讀音可混淆,不引入任何新的拒絕風險,也不多花提示詞 token。
- **判斷交給看得到上下文的一方**:符合專案方向(內容判斷靠 LLM 的語境理解,不寫機械規則)。

### 4.3 已知代價

每次拒絕消耗一次完整生成呼叫(約 30 秒)。成本有界——8 組動詞、每句最多被拒一次(failure 紀錄擋住重試),屬一次性支出。若實測拒絕率過高導致跑批過慢,再加**方案 C 作為便宜的前置過濾**(見下),方案 A 仍是正確性的最後防線。

### 考慮過但放棄

- **B. 選句階段批次預判**(一次 LLM 呼叫判 20 句):便宜,但判斷時只看得到單句、看不到上下文,準確度低於 A;且新增元件與快取/錯誤處理。除非未來同表層動詞大幅增加,複雜度不值得。
- **C. 人工設定檔分流**(擴充 `extra_search_keywords.json` 的排除規則):零 LLM 成本、行為可預測,但 18 張母卡都要人工維護、語料更新要重調,且只擋得住已知句型。**保留為 A 的可選前置過濾**,不作為主方案。
- **D. 搭配語硬規則**(`名を`→けがす、`服`→よごす):典型的機械檢查與過擬合,規則永遠寫不完,與專案方向相悖。

### 回歸測試

- `canonical_verb_reading`:`纏[まと]める` → `まとめる`;純假名不變;非平假名輸入拒絕
- 唯一鍵遷移冪等:重跑 `init_db.py` 不重複建索引
