## 1. 現況

**誰在寫媒體到 Anki**

| 來源 | 做法 | 檔名 |
|---|---|---|
| TG 錄音評分 | 下載 TG 語音（`.ogg`），經 `AnkiClient.store_media_file` 存進 Anki，再以 `add_recording` 寫進 `Recordings` | `rec_{Card_ID}_{UTC 時間}.ogg`（`voice.py:134`） |
| TG 上傳音檔 | 同上存檔，再以 `add_audio` 寫進 `Prompt_Audios`／`References` | 同上 |
| TG 自訂頭像 | 照片存一份在後端 `app/assets/avatars/`，再上傳到 Anki；之後從那個資料夾列出供選 | `avatar_{chat_id}_{UTC 時間}.jpg`（`media.py:78`） |
| 本機批次腳本 | 從本機目錄讀檔，經 AnkiConnect `storeMediaFile` 上傳 | `{source_game}_{原檔名}` |

**網頁**

- 只能讀：`GET /anki-media/{filename}` 只回應音訊、影片、圖片類型，Cards 頁顯示卡面時用。
- 不能寫：沒有上傳到 Anki 的端點。
- 現有的 `/storage/*` 是存到 MinIO，不是 Anki 媒體資料夾，repo 內也沒有呼叫方，不能拿來用。

**handlers 計畫書的現況**：網頁建卡只收文字；handler 宣告的媒體欄位（`MEDIA_FIELDS`，例如 `_v2` 的 `Word_Audio`、`Target_Example_Audio`）在建卡表單不列、建出來留空，`PATCH` 拒絕直接修改，網頁上唯讀。

## 2. 目標與非目標

**目標**

- G1 網頁可以上傳音檔、圖片到 Anki 媒體資料夾，也可以在瀏覽器直接錄音。
- G2 **上傳和使用分開**：一個上傳端點，給建卡、JSON 欄位編輯、動作（例如對話卡加音檔）共用。
- G3 **不會蓋掉別人的檔案**：檔名一律由後端產生。
- G4 **要不要上傳由 handler 決定**：只有宣告了媒體參數或媒體欄位的地方，前端才顯示上傳元件。

**非目標**

- 改 TG 與本機腳本的上傳方式。
- 清理沒被引用的媒體檔（交給 Anki 的「檢查媒體」）。
- TTS 產生語音（卡片模板上的「透過 AI TTS 生成語音」按鈕，另案）。
- 列出、挑選 Anki 裡已有的媒體檔（例如頭像庫）：之後若需要再加查詢端點。

## 3. 設計

### D1 兩步驟：先上傳，再使用

```text
1. POST /api/v1/media                     上傳檔案 → 回傳後端產生的檔名
2. POST /handlers/{name}/notes            建卡，params 裡填那個檔名
   PUT  /handlers/{name}/notes/{id}/json/{field}     JSON 欄位，某筆資料的媒體鍵填那個檔名
   POST /handlers/{name}/notes/{id}/actions/{action} 動作，參數填那個檔名
```

前端可以把兩步包成一次「送出」，使用者感覺不到。

為什麼不在建卡請求裡直接夾帶檔案（multipart）：

- 建卡、JSON 編輯、動作的請求都維持 JSON：驗證、422 指到欄位、`create_schema` 產生表單都建立在 JSON 上，混入檔案就要另外處理。
- 一個上傳端點三處共用，不必各做一套。
- 建卡失敗（例如首欄位重複）時，檔案已經上傳好，修正後再送不必重傳。

~~代價：上傳後放棄或建卡失敗，媒體資料夾會留下沒被引用的檔案；Anki 的「工具 → 檢查媒體」可以清掉，影響很小。~~

**2026-11-14 改為「建卡與媒體一起成功、或一起不寫」**：第 1 步只把檔案放在後端的暫存區，**不寫進 Anki**；
第 2 步的請求成功時才把用到的檔案存進 Anki，失敗時撤回，Anki 和送出前一樣（見 §6.6）。上傳後放棄、換檔、
建卡失敗都不會在 Anki 留下檔案；建卡失敗時暫存檔留著，修正後再送仍不必重傳。

### D2 `POST /api/v1/media`

請求：`multipart/form-data`，欄位 `file`（單一檔案）與 `kind`（`audio` 或 `image`）。

回應（201）：

```json
{ "filename": "web_audio_20261020_153012_3f9a1c.mp3", "kind": "audio", "size": 48213 }
```

處理順序：

1. **檢查類型**：依檔案內容判斷，不只看副檔名。
   - `audio`：接受 mp3、ogg、wav、m4a、webm（瀏覽器錄音）。
   - `image`：接受 jpg、png、webp。
2. **檢查大小**：超過上限回 413（上限見 §5 待決 2）。整個檔案要以 base64 經 AnkiConnect 傳送，太大會拖慢甚至失敗。
3. **轉檔**：Anki 不一定能播 webm、m4a，統一用後端既有的 `FfmpegClient.convert_to_mp3`（錄音評分已在用）轉成 mp3；mp3、ogg、wav 原樣保留（ogg 是 TG 語音的格式，Anki 能播）。圖片不轉。
4. **產生檔名**：`web_{kind}_{UTC 時間}_{隨機 6 碼}.{副檔名}`。前綴 `web_` 和 TG 的 `rec_`、`avatar_`、腳本的 `{source_game}_` 區分開，看檔名就知道從哪裡上傳的。
5. ~~經 `AnkiClient.store_media_file` 存進 Anki。~~ 放進後端暫存區（2026-11-14 起；建卡或修改成功時才存進 Anki，見 §6.6）。AnkiConnect 的 `storeMediaFile` 遇到同名檔會**直接覆蓋**，所以第 4 步一定由後端產生、不採用使用者的檔名。
6. 不做寫入後同步：媒體檔會隨下一次寫入筆記時的同步一起上傳到 AnkiWeb。

錯誤：

| 情況 | 狀態碼 | `error_code` |
|---|---|---|
| 類型不符或無法辨識 | 415 | `MEDIA_TYPE_UNSUPPORTED` |
| 超過大小上限 | 413 | `MEDIA_TOO_LARGE` |
| 轉檔失敗 | 422 | `MEDIA_CONVERT_FAILED` |
| ~~Anki 寫入失敗~~ | ~~502~~ | 2026-11-14 起上傳不碰 Anki；Anki 的錯誤改在建卡、修改時回報 |
| 後端沒有 ffmpeg | 503 | `MEDIA_CONVERTER_UNAVAILABLE`（審查後新增） |

掛 `verify_api_key`，與其他 `/api/v1` 端點相同。

### D3 handler 宣告「這裡要上傳」

三個使用處各有宣告方式，前端看到宣告才顯示上傳元件：

| 使用處 | 宣告 | 前端顯示 |
|---|---|---|
| 建卡（標準的手動填表） | handler 的 `MEDIA_FIELDS` 由「名稱清單」擴充成「欄位名 → 種類」，例如 `{"Word_Audio": "audio"}` | 該欄位顯示上傳／錄音元件；送出時填 `[sound:檔名]`（音檔）或 `<img src="檔名">`（圖片） |
| 建卡（覆寫的 `CreateParams`） | 參數欄位標 `json_schema_extra={"x-ui": "audio"}` 或 `"image"` | 同上；送出時填純檔名，由 handler 自己組欄位 |
| JSON 欄位的某個鍵 | 資料模型的欄位標 `x-ui: audio`／`image`（JSON 欄位設計書裡原本先標成唯讀的 `media`） | 那一筆的那個鍵顯示上傳元件 |
| 動作參數 | 具名動作的參數模型標 `x-ui`（動作參數模型化之後） | 同上 |

- 一般欄位存 `[sound:檔名]` 或 `<img src="檔名">` 是 Anki 的慣例，卡片模板直接顯示；JSON 欄位裡存純檔名，由模板自己組（例如對話卡 `Recordings` 的 `audio` 鍵）。這個差異由宣告決定，前端不必猜。
- **服務層再檢查一次**：媒體欄位或參數填入的檔名必須符合 D2 的命名格式（`web_…`）或欄位原本就有的值，否則 422。避免使用者手填一個不存在或別人的檔名。
- 媒體欄位在 handlers 計畫書裡是「`PATCH` 拒絕直接修改」；本設計實作後，改成「只能填 `/media` 產生的檔名」。

### D4 前端元件

- **上傳**：選檔或拖放；顯示檔名、大小、上傳進度；音檔上傳後可以試聽，圖片顯示縮圖。
- **錄音**（`audio`）：瀏覽器 `MediaRecorder` 錄製（產出 webm），停止後可試聽、重錄，確定後上傳（後端轉 mp3）。
- 上傳成功後，元件把回傳的檔名填進對應的參數或欄位；整張表單送出前，若還有上傳中的檔案，送出按鈕停用。
- 錯誤（413、415、422）顯示在元件旁。

### D5 第一個接上的地方

建議從單字卡 `_v2` 的建卡開始（handlers 計畫書的試點）：`Word_Audio`、`Target_Example_Audio` 兩個音檔欄位。資料平坦、沒有 JSON，最容易驗收。

之後依序：

1. 對話卡、三語卡的 `add_audio` 動作（web_ui_parity 階段 D）：要先完成動作參數模型化與 `ValueError` 改 4xx（階段 B）。
2. JSON 欄位裡的媒體鍵（`Recordings` 的 `audio` 等）：接在 JSON 欄位設計書之後。
3. 網頁建 jp 子卡（handlers 計畫書 D7「之後網頁要做時」）。

## 6. 實作紀錄（第一階段，2026-11-14）

### 6.1 做了什麼

- `POST /api/v1/media`（D2）：檢查大小、依內容判斷格式、webm／m4a 轉 mp3（轉完再檢查一次大小）、後端產生檔名、放進暫存區；`GET /api/v1/media/{檔名}` 讀回還沒用掉的上傳（預覽用）。建卡、修改成功時才存進 Anki（§6.6）。
- handler 的 `MEDIA_FIELDS` 由名稱清單改成「欄位 → 種類」（D3）；`GET /handlers` 的 `media_fields` 跟著改成物件。
- 標準建立（手動填表）：媒體欄位列進 `create_schema` 並標 `x-ui`；送出的值是上傳取得的檔名，後端包成 `[sound:檔名]` 或 `<img src="檔名">`。
- 修改欄位（`PATCH`）：媒體欄位可以換成上傳取得的檔名、清空，或原樣送回（不變）。其他值回 422 `MEDIA_FIELD_INVALID`。
  檢查的是檔名**格式**（`web_{種類}_…`、副檔名屬於該種類），不確認檔案真的在 Anki 裡。
- 前端 `MediaField` 元件（D4）：選檔、拖放、進度、試聽／縮圖、錄音（試聽、重錄、放棄）、錯誤顯示；上傳中、等待麥克風授權、錄音中、錄好還沒決定時不能送出表單，元件裡的其他按鈕也停用。
- 接上的地方：單字卡建卡的 `Word_Audio`、`Target_Example_Audio`（D5 的第一個目標）；筆記欄位彈窗裡所有宣告了媒體欄位的卡片——單字卡的兩個音檔、人脈卡的 `Photo`（backlog F6 的「修改既有卡片的照片」）。

### 6.2 與設計的差異與補充

| 項目 | 設計 | 實作 | 原因 |
|---|---|---|---|
| 誰把檔名包成 `[sound:…]` | D3 寫「送出時填 `[sound:檔名]`」 | 前端一律送純檔名，後端檢查後再包 | 檢查只需要認一種寫法；前端不必知道 Anki 的標記；和覆寫 `CreateParams` 的 handler 行為一致 |
| 媒體欄位填錯的狀態碼 | 「否則 422」 | 422，新增 `error_code`：`MEDIA_FIELD_INVALID` | 原本沒有指定錯誤碼 |
| 媒體欄位檢查的強度 | 「避免使用者手填一個不存在或別人的檔名」 | 只檢查格式：擋得掉手打的名字與 TG、腳本的檔名，格式正確但不存在的名字會通過（卡片上只是播不出來） | 確認存在要多問一次 Anki；格式檢查已擋住實際會發生的誤填 |
| 人脈卡 TG 的 `set_photo` | 未提 | 不套用上一列的檢查，只擋不安全的字元 | TG 頭像的檔名是 `avatar_…`；網頁的修改欄位才走新規則 |
| webm、m4a 轉檔的輸入 | 沿用 `FfmpegClient.convert_to_mp3`（從 stdin 讀） | 新增 `convert_file_to_mp3`，先寫成暫存檔再轉；最長 90 秒，逾時中止 ffmpeg | m4a 必須（索引常在檔尾，ffmpeg 從 stdin 讀不到），webm 為了統一一起改；暫存檔轉完即刪 |
| 大小上限套在哪裡 | 「超過上限回 413」 | 轉檔前檢查上傳的大小，轉成 mp3 後再檢查一次 | 低位元率的錄音（opus 語音）轉成 mp3 會變大好幾倍，實際送進 Anki 的是轉檔後的檔案 |
| 同一個容器的圖片 | 未提 | HEIC、AVIF（和 m4a 同為 `ftyp` 容器）不當成音檔收 | 避免把照片送去轉 mp3 |
| 後端沒有 ffmpeg | 未提 | 找不到或無法啟動 ffmpeg 回 503 `MEDIA_CONVERTER_UNAVAILABLE`，訊息請使用者改傳 mp3、ogg、wav；不需轉檔的格式不受影響。檔案本身轉不了（含逾時）才是 422 `MEDIA_CONVERT_FAILED` | 前者是伺服器的問題，換檔案沒有用；本機開發不一定裝了 ffmpeg，正式機映像檔有 |
| Anki 存檔時改了檔名 | 未提 | 建卡、修改時回 502，撤回這次存進去的檔案、不寫筆記 | 改過的名字和欄位裡填的對不上 |
| 既有的非單一檔案內容 | 未提 | 欄位裡是多個音檔或夾了文字時，照原樣顯示、不預覽；上傳新檔會整個取代 | 腳本寫入的欄位不一定是單一檔案 |
| 錄音長度 | 未提 | 最長 5 分鐘，到了自動停止 | 避免忘了按停止 |
| 錄音的狀態 | D4 只寫「錄製、試聽、重錄」 | 另有「正在開啟麥克風」：等使用者允許期間，元件和表單都不能操作；每段錄音的麥克風各自放開 | 等授權時還能選檔，會讓錄音和上傳互相蓋掉狀態、麥克風在背景一直開著 |
| 寫入前的同步 | 「不做寫入後同步」 | 上傳沒有同步；建卡、修改時 `AnkiClient.store_media_file` 會在存檔前觸發一次有防抖的同步（TG 上傳也一樣），寫完筆記再照常同步 | 沿用既有行為，沒有改 |

### 6.6 建卡與媒體一起成功、或一起不寫（2026-11-14）

原本上傳就直接存進 Anki，建卡失敗或放棄時 Anki 會留下沒被引用的檔案。改成：

| 時間點 | Anki | 後端暫存區 |
|---|---|---|
| 上傳（`POST /media`） | 不動 | 放進檔案 |
| 送出建卡或修改：寫筆記**之前** | 存進用到的檔案 | 留著 |
| 寫筆記成功 | 檔案留著（筆記用到） | 刪掉 |
| 寫筆記失敗（重複、欄位錯誤、Anki 拒絕、請求中斷） | 刪掉這次存進去的檔案 → 和送出前一樣 | 留著，修正後直接重送 |
| 上傳後放棄、換檔、沒送出 | 不動 | 一天後自動清掉 |

- 程式：`app/services/media_staging.py`（暫存區）、`app/services/media_commit.py`（存進 Anki、撤回），`NoteService.create`、`update_fields` 用它包住 handler 的寫入。只包筆記本身的寫入：加標籤、建立後的後續處理、同步在筆記寫成之後，失敗只回提醒，不算建卡失敗。
- 撤回前會查有沒有筆記用到這個檔案，有就不刪。例如 Anki 回應逾時但其實寫進去了，或同一個檔案上次其實建成功、這次重送才撞到重複。查詢或刪除本身失敗時也不刪（記 warning），檔案留在 Anki：這是唯一還可能留下沒被引用的檔案的情況，前提是 Anki 在寫筆記失敗後又連不上。
- 送出時用到的上傳不在暫存區（超過一天、後端重新部署過、已經用在別張卡）：回 410 `MEDIA_UPLOAD_EXPIRED`，什麼都不寫；網頁預覽也會顯示「已經不在了，請重新上傳」。
- 暫存區在後端容器的暫存目錄：**重新部署或重啟後就清空**，表單裡還沒送出的上傳要重傳。
- 修改欄位時換掉的舊檔案不刪：可能還有其他筆記在用（和以前一樣）。
- 測試：`tests/test_media_upload.py` 的 `TestStaging`、`TestCommit`；`tests/test_handlers_api.py` 的建卡、修改失敗後 Anki 沒有留下檔案、重送成功、有筆記用到時不刪、上傳過期回 410。
