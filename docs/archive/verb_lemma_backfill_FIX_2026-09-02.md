## 1. 症狀與復現

- **症狀**:同一張母卡的動詞在 DB 裡有多種拼寫並存——母卡欄位是「止める」,DB 卻存了命中它的假名關鍵字「やめる」;母卡「纏める」在 DB 有 `纏める` / `まとめる` / `纏[まと]める` 三種。查重程式把它們當成不同動詞,同一句台詞因此可以被同一母卡重複生成(2026-09-02 全庫比對出 7 組、8 張真重複,已於同日刪除較差的一張)。
- **卡片本身無問題**:母卡、子卡、翻譯、活用說明全部正確,差別只在 DB 這一個欄位沒有標準化。
- **首次出現**:2026-08 假名擴展關鍵字(`extra_search_keywords.json`)上線後大量出現(147 筆);帶標音的 3 筆分別為 7 月初(320、321)與 8/31 刪卡工具鏈完整性修復補入(745)。

## 2. 根因(已定位)

三個寫入點各寫各的字串,沒有共用一條正規化規則:

| 寫入點 | 寫入的拼寫 | 存量 |
|---|---|---|
| 生成管線,母卡標準表層命中 | `止める`(正確) | 絕大多數 |
| 生成管線,**假名擴展關鍵字**命中(`generate_child_cards.py` 以 `kd["keyword"]` 寫入) | `やめる`、`まとめる`、`かかる`… | **147 筆** |
| 刪卡工具鏈完整性修復(`profiles._verb_pair_lemma` 直接回傳 Verb_Pair_JSON 的帶標音值) | `纏[まと]める` | **3 筆** |

程式碼層修法(統一寫入規則 + 句子文字層去重)在關聯文件的分支處理;**本文件只負責存量資料**。

## 3. 修法

把每筆紀錄的 `verb_lemma` 改成**母卡標準表層去標音**,原值搬到新欄位 `search_keyword`(需先以 `init_db.py` 補上該欄位,2026-09-02 本機已補)。映射依據:去 `[標音]` 括號;若值落在該母卡 `extra_search_keywords.json` 的 `extra_keywords` 內,映射回其標準表層。

改寫後若與同一台詞的另一筆撞唯一鍵 `(script_id, verb_lemma, project)`:

- **一活一死**(死 = 已軟刪除):保留活的並改名,硬刪死紀錄,`delete_count` 保留為 1 記住「這句曾被刪過一張」。本清單 8 組全屬此類(其中 7 組是同日刪除較差重複卡留下的,[156]/[479] 一組原本就是死紀錄)。
- **兩筆皆活**:拒絕執行——這代表真重複卡還在,須先刪卡。**目前 0 組**(2026-09-02 dry-run 確認)。

兩種執行方式擇一:

1. 修復腳本(在 `fix/dedup-key-master-note-id` 分支):
   ```
   python backend/scripts/common/database/canonicalize_verb_lemma.py            # dry-run,輸出應與 §4 一致
   python backend/scripts/common/database/canonicalize_verb_lemma.py --execute
   ```
2. 直接執行 §4.3 的等價 SQL(不依賴任何分支)。

### 考慮過但放棄

- **只刪 DB 紀錄、卡片留著**來解真重複:那張卡會變成「Anki 有、DB 沒有」的未追蹤卡,完整性檢查會再替它補紀錄、再撞鍵。所以真重複一律連卡刪(已完成),死紀錄才能純 DB 合併。
- **保留假名拼寫不改,只在查重時做正規化**:等於每個讀取點都要記得正規化,和這次「多寫入點各寫各的」是同一類問題的鏡像。資料層存正規值才是單一事實來源。
