# ADR 005: 嚴格狀態驅動的 Telegram Bot 卡片新增流程 (Strict State-Driven Telegram Bot)

## 狀態 (Status)
**已接受 (Accepted)** - 實作於 Phase 11 (2026-07-13)

## 脈絡 (Context)
在早期的架構設計中，Telegram Bot 的卡片新增流程採用了「無狀態兜底 (Stateless Fallback)」的設計模式。具體而言：
1. 若使用者透過 `/newcard` 觸發選單，再點選特定功能，會進入特定的處理流程。
2. 若使用者未觸發任何功能，直接發送一段文字，系統會透過 `messages.py` 作為兜底，並假設這段文字是「要查詢的單字或片語」，然後直接拋給 LLM 去生成單字卡。
3. 若文字為 JSON 格式，則會假設為 `Speaking_Coach_Dark` 卡片的 Payload，直接解析並建立卡片。

這樣的設計初衷是為了讓「查單字」這個最高頻的操作變得極致簡單（即傳即查）。然而，隨著系統卡片類型增加，這個設計暴露了嚴重的缺陷：
- **誤判率高**：當使用者只是想在對話中回覆普通訊息，或是誤傳了一段文字，系統會硬將其拿去查字典，並生成一張毫無意義的卡片（如 "不符合 TOEIC_Coach_Dark 欄位的提示"）。
- **除錯困難**：當卡片生成失敗時，很難區分是「格式錯誤」、「LLM 解析失敗」還是「根本就不是要建卡片」，這導致錯誤提示經常風馬牛不相及（例如明明是想建 Speaking 卡片，卻因為 JSON 錯誤而掉入單字卡兜底，最後回報 TOEIC 卡片錯誤）。
- **狀態混亂**：系統難以明確得知使用者的「意圖」，只能透過正則表達式或 JSON 解析來進行脆弱的猜測。

## 決策 (Decision)
我們決定全面放棄「無狀態兜底」設計，將 Telegram Bot 的所有卡片新增流程改為 **嚴格的狀態機 (FSM) 驅動架構**。

具體實作方針：
1. **單一入口**：所有的卡片新增（包含 TOEIC 單字卡、Speaking 對話卡、外語糾錯卡）都必須透過 `/newcard` 呼叫選單來明確啟動。
2. **統一 FSM 套件**：在 `backend/app/bot/handlers/fsm/` 下建立專屬的狀態機套件，每種卡片類型對應一個 `_fsm.py` 檔案（如 `vocabulary_fsm.py`, `speaking_fsm.py`）。
3. **明確狀態過渡**：使用者必須處於特定的狀態（例如 `VocabularyStates.waiting_for_word`）下發送文字，系統才會將其視為對應的輸入。
4. **防呆兜底**：`messages.py` 不再執行任何自動生成邏輯。如果使用者在「無狀態」的情況下發送純文字，`messages.py` 會直接攔截，並友善地提示使用者：「未知的文字。請使用 /newcard 開啟選單」。

## 影響 (Consequences)

### 正面影響 (Positive)
- **零誤判**：系統再也不會因為使用者的一句閒聊或誤輸入而產生垃圾卡片。
- **錯誤提示精確**：因為狀態是隔離的，如果使用者在輸入 JSON 時格式錯誤，系統能準確地給出 Speaking_Coach 的錯誤提示，而不會掉進別的卡片邏輯。
- **維護性提升**：所有對話流程集中於 `fsm/` 目錄，職責單一，且使用 aiogram 官方的 `StatesGroup`，符合現代 Telegram Bot 的最佳實踐。
- **跨平台輸入支援**：FSM 架構使得收集多行輸入、分步驟問答變得極為容易（例如先問情境，再問範例），不再需要強迫使用者手刻難懂的 JSON。

### 負面影響 (Negative)
- **操作步驟增加**：使用者無法再像以前一樣「打開 Bot 直接貼單字就生成」，必須先點擊或輸入 `/newcard` 並選擇「單字卡」後才能開始輸入。不過，考量到可靠性的提升，這點犧牲是值得的。
